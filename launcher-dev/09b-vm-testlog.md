### 7.0 根因：VM 用 NAT 时两端 IP 相同，EasyTier 连回自己（2026-10-28 16:38 查明）

**这是今天所有"能加入却进不去 / 反复超时踢人"的根因，属测试环境构造问题，不是产品缺陷。**

VM 网络选的是 **NAT 共享主机 IP**，宿主上 `VMnet8 = 192.168.x.1`，路由表里没有 `192.168.x.5`，
`ping 192.168.x.5` 100% 丢包。于是 VM 里的 EasyTier 对外报出的端点就是**宿主自己的 `192.168.x.9`**。

宿主的 `netstat` 直接抓到了自我连接：

```
TCP  192.168.x.9:6093  →  192.168.x.9:9366  ESTABLISHED     ← 源=目标=宿主 IP
```

因果链完整对得上：

| 现象 | 由 NAT 共享 IP 解释 |
|---|---|
| `[ScaffoldingServer] Connection closed: Os { code: 10060, TimedOut }` | 连回自己，该端口无人应答 → 超时 |
| `[RoomExperiment] Removing guest … timeout` | 控制通道建不起来，心跳收不到 → 按超时踢人 |
| 游戏登录后立刻 `lost connection: 连接中断` | 数据面走回环/公网中继，握手包过不去 |
| 宿主游戏日志源地址一律为 `192.168.x.9` | NAT 把 VM 流量伪装成宿主 IP |
| **本机代理（`127.0.0.1:6077`）能进** | 该通路不依赖对端地址，故不受影响 |

**结论**：做联机测试时 VM 必须用**桥接**（VM 拿到独立 IP，如 `192.168.x.5`），
NAT 模式会让 EasyTier 两端地址相同、连回自身。真实用户是两台不同的机器，不会出现这种拓扑。

**验证（2026-10-28 16:43 切换后）**：从 NAT 改为桥接、且**桥接目标必须选物理网卡**（用户最初误选到虚拟网卡，
现象与 NAT 相同）。切换后自连消失，`netstat` 变为：

```
TCP  192.168.x.9:6093  →  192.168.x.5:52576  ESTABLISHED     ← 到 VM 的真实 P2P
TCP  192.168.x.9:6105  →  203.0.113.10:39409 ESTABLISHED     ← 公网中继（备用）
ping 192.168.x.5 → 1ms，0% 丢包
```

「宿主能看到 `192.168.x.9 → 192.168.x.9` 自连」可直接判定为网络模式配错，不必再查陶瓦或游戏。


**顺带**：本环境下实际可用的是"陶瓦本机代理"通路（`127.0.0.1:<代理端口>`），
所以界面提示里那句「或用『直接连接』填 {S.Url}」不是可选项，而是**故障时的必经通道**——
建议后续把它做成更醒目的指引，而不是并列的第二方案（记入 `08` 改进项）。

### 7.1 端到端连通成功（16:32，`custom.3`）

宿主游戏日志的**登录行**是唯一硬判据，本次已拿到：

```
[16:32:29] 233[/127.0.0.1:8169] logged in with entity id 2611 at (-8.699, 72.0, 7.300)
[16:32:54] 233 lost connection        ← 用户主动退出，非掉线
```

同一时段内失败与成功两种来源地址并存，是本节最有价值的观察：

| 时间 | 宿主看到的来源 | 结果 |
|---|---|---|
| 16:30:18 | `192.168.x.5:54344` | 连接中断（VM 直连宿主 LAN 端口） |
| 16:30:30 ~ 16:31:57 | `192.168.x.9:7627 / 7690 / 7721 / 8008 / 8031` | 全部「连接中断」（经 EasyTier 用户态转发，源地址呈宿主自身 IP） |
| **16:32:29** | **`127.0.0.1:8169`** | **登录成功**（走本机代理端口） |

**判读**：陶瓦的两条通路质量不等价——**走本机代理（`127.0.0.1`）能进游戏，走 EasyTier 用户态转发（源址呈宿主 LAN IP）会在握手阶段被重置**。这与当日 16:13–16:28 反复出现的
`[ScaffoldingServer] Connection closed: Os { code: 10060, TimedOut }` + `Removing guest … timeout` 是同一现象。

**仍未定位**：为何用户的操作会落在那条失败通路上（点「陶瓦联机大厅」条目 vs 「直接连接」、以及开局域网的次数），
需要专门复现才能定论。**记为待查**，不据此判定产品缺陷——用户从「直接连接」改用代理端口即可连通。

**T-05b 的恢复路径已确认可用**：断网失败 → 恢复网络 → **直接点「加入」（未点关闭陶瓦）→ 成功加入房间**，
说明 `TcEnsureIdle` 复位修复生效（`custom.3`）。

**T-05b 暴露的恢复路径问题（2026-10-28 用户实测发现）**：游客断网失败后，**恢复网络并不能直接重试**——
点「加入」没反应，必须点「关闭陶瓦」重启守护进程、重新粘码才能进。

根因在代码：`TcStartHost` / `TcJoin` 拿到端口后直接发 `/state/scanning` 或 `/state/guesting`，
**没有先复位**。而陶瓦是状态机，上一次失败会停在 `exception` / `guesting` 等非空闲态，此时再切状态会被拒。
已在 `ModCustom.vb` 加 `TcEnsureIdle(Port)`（切状态前先发 `/state/ide`，失败不阻断），建房与加入两处都调用。
**待验证**：用新构建重复"断网失败 → 恢复网络 → 直接点加入"，应能成功，无需关闭陶瓦。

### 7.2 T-06 稳定性（16:43:52 → 16:58:56，15 分钟，**未跑满 30 分钟**）

桥接修正后重测。基线 `Removing guest=4` / `Timeout10060=3`（NAT 期间累积，非本轮）。

| 采样 | PCL | java | terracotta | easytier | 到 VM 连接数 | Removing guest | 10060 |
|---|---|---|---|---|---|---|---|
| 16:43:52 | 110 MB | 1411 MB | 13 MB | 27 MB | 1 | 4 | 3 |
| 16:48:53 | 89 MB | 1330 MB | 13 MB | 26 MB | 1 | 4 | 3 |
| 16:53:54 | 80 MB | 1147 MB | 13 MB | 25 MB | 1 | 4 | 3 |
| 16:58:56 | 73 MB | 1341 MB | 13 MB | 25 MB | 1 | 4 | 3 |

**判读**：15 分钟内**零新增踢人、零新增超时**，P2P 连接恒为 1 条，四个进程内存全程持平或下降
（`java` 在 1147–1411 MB 间随 GC 波动，属正常；`PCL` 从 110 降到 73 MB 是 GC 回收）。
**无内存泄漏、无掉线迹象。**

**中止原因**：虚拟机资源不足，游客端游戏被关闭——**属测试环境限制，不是产品问题**。
要跑满 30 分钟需降低游客端负载（小窗口、视距 2、关粒子），或提高 VM 配置。

**结论**：按 15 分钟数据判 **通过（部分证据）**，30 分钟长时结论待有条件时补。

### 7.3 T-05c 房主中途直接关游戏（17:04，**通过，但文案不足**）

操作：游客已在世界内（`17:03:40 233[/127.0.0.1:15542] logged in, entity id 6175`），
房主**直接点窗口 ✕ 关掉游戏**（未点停止联机、未点关闭陶瓦）。

三方时间线（3 秒一档高频采样）：

| 时刻 | 宿主观测 | 说明 |
|---|---|---|
| 17:04:27 | `host-ok`、`java=1` | 最后一条正常样本 |
| 17:04:30 | 游戏日志 `Saving players` → `Stopping singleplayer server as player logged out` | **房主关窗** |
| 17:04:32 | `java=0`（进程消失），陶瓦仍 `host-ok` | 守护进程还在，但没察觉世界没了 |
| 17:04:57 | `/state` → **`exception`**（index 14→15），`easytier` 进程退出 | **延迟 27 秒**才切状态 |
| 游客侧 | MC 原生界面「**连接已丢失**」/ 副标题「**连接中断**」/ 按钮「返回到服务器列表」 | 数秒内出现 |

**判定**：

- **感知及时 — 通过**：游客在数秒内看到明确断线界面，不会卡在加载或假装在线。
- **文案不足 — 记改进项**：这是 Minecraft **原生**的通用断线提示，信息量为零：
  既没说"房主关闭了游戏"，也没提示"房间已失效，请向房主索要新码"，更没有重试引导。
  玩家只会认为"网络又抽了"，然后反复点「返回到服务器列表」重连一个已死的房间。
- **宿主侧延迟 27 秒**才从 `host-ok` 掉到 `exception`，且 `easytier` 也随之退出；
  陶瓦守护进程本身**存活**（`terracotta=1` 全程）。这解释了为什么失败后直接重试无效——
  守护进程停在 `exception` 而非 `waiting`，必须靠 `TcEnsureIdle` 复位。

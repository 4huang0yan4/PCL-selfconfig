# ADR-0001 基座策略：继续增强 PCL 分支，还是逐步自研

- 状态：**Accepted**（2026-10-27 用户拍板采用 C）
- 日期：2026-10-27
- 关联：`04-tech-decisions.md` 的 P1、P2、P3

---

## 背景

当前项目以 PCL 2.99.0.0 开源版为基座自编译，自用功能通过 `custom\` 覆盖层（23 个完整文件）与 `Modules\ModCustom.vb` 实现。已完成：解除下载限制、主题解锁、百宝箱、凭据卡、下载源自定义、视频背景、联机页、5 篇帮助。

接下来的五项需求（R2 MCBBS v2、R3 Terracotta、R4 mrpack、R5 安全、R6 联机抽象）有一个共同特征：**它们都不是"改 PCL 的某一行"，而是"新增一块能力"**。

PCL 的架构是"全局配置 + 版本目录"，不是"实例为中心的抽象"。这带来两个具体摩擦：

1. 导出整合包需要读取"实例全貌"（哪些 mods、什么加载器、什么 Java），而 PCL 的这些信息散在版本 json、`Setup.ini`、注册表三处。
2. 联机若要做成可插拔，需要一个稳定的"方案提供者"接口；PCL 的联机页是硬编码的外挂工具启动。

## 选项

### A. 继续在 PCL 分支内做（全用 `custom\` 覆盖）

- 优点：零迁移；四条链路（下载/安装/启动/整合包）现成；与上游可对照。
- 缺点：新能力要塞进 PCL 的页面与模块结构；VB.NET + net48 生态偏旧；每次上游同步需人工比对 23 个文件；架构摩擦长期存在。

### B. 以 PCL 为参考，重写核心、自建界面

- 优点：架构自由（可照 Prism 的 `BaseInstance`）；可用 .NET 8 + C#；分析器与工具链现代化。
- 缺点：工作量以月计；四条链路全部重做；个人自用场景收益存疑；一旦重写，现有 5 篇帮助与界面打磨全部作废。

### C. 渐进：新能力写在新层，旧链路仍走 PCL（**倾向**）

- 做法：新建独立工程（同解决方案内），只读方式消费 PCL 的实例信息；新层实现导出、联机抽象、安全扫描；PCL 主体不动或极少动。
- 优点：R1/R8 已可用，不必重做；R2/R3/R4 天然是增量；风险可控，任何一步失败都能退回 A。
- 缺点：双栈并存期长；需要先定义接口（`IInstanceView`、`IMultiplayerProvider`），否则会退化成 A 的"到处塞代码"。

## 决策

**采用 C（渐进式）。** 2026-10-27 用户确认："C，然后按优先级，逐步实现"。

具体约束（从现在起的新代码一律遵守）：

1. **新能力只写在新层**，不往 PCL 页面里塞业务逻辑；PCL 主体（`build\Plain Craft Launcher 2`）只在"必须挂载入口"时改极少量代码，且改动要集中在 `ModCustom.vb` 或 `custom\` 覆盖文件里。
2. **只读消费 PCL 状态**：新层通过只读视图（`IInstanceView` 一类）拿实例信息，不直接写 PCL 的存储。
3. **接口先行**：任何新功能开工前，先定它消费/暴露的接口，再写实现。
4. **可回退**：新层任何一个功能失败，都应当能停用它而不影响 PCL 原有功能。

## 后果

- 需要新增工程与解决方案结构；`pcl-src\build` 保持不变，新工程引用其输出或直接引用源码。
- `P2`（迁 .NET 8）只在新层做，PCL 主体留在 net48。
- 接口先行：`IInstanceView` 与 `IMultiplayerProvider` 必须先于任何实现代码。
- 短期成本：双栈并存，调试时要区分"问题在 PCL 还是在新区"。缓解办法是新层功能一律可关闭。

## 什么情况下推翻本决策

- 若 R2/R3/R4 中任意两项在"新层只读消费"模式下被证明需要 PCL 内部写权限（例如必须改 `ModComp.vb` 的私有状态），则 C 不成立，回到 A 或转 B。
- 若用户对界面/体验提出结构性要求（例如要求实例中心式首页），则 B 的收益上升，需重新评估。

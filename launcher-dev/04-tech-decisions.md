## 已决策（D 系列）

### D1 技术栈：.NET（VB.NET / WPF 为主，C# 可用）

`[已确认]` 与 PCL 生态一致，便于参考与移植；WPF 的界面能力足够，换 UI 框架收益不足以抵消迁移成本。

### D2 目标运行环境：仅 Windows 10+

`[已确认]` 目标用户就是本机（Win10 19045 x64）。跨平台需要重写平台层（HMCL 的三层架构就是为跨平台付的成本），本项目不承担。

### D3 联机必须可插拔

`[已确认]` 后端可能更换（Terracotta / EasyTier / 外部工具），主程序不得写死其一。详见 `06-multiplayer.md`。

### D4 不发明私有格式

`[已确认]` 整合包与实例格式一律对齐既有标准。迁移能力来自"能读懂"，不是"能导出自己的"。

### D5 工具链锁 .NET SDK 8.0.404

`[已确认]` 本机 Win10 19045 缺 CET 更新：SDK 10 报 `Your Windows doesn't fully support CET`，SDK 9 已 EOL。编 net48 须显式给 `TargetFrameworkRootPath`。工具链在 `gongtong\_tools\dotnet`，不进 PATH。

### D6 目录自足布局

`[已确认]` `gongtong\` 下三者同级：`pcl-src\`（源码）、`_tools\`（工具链）、`PCL-custom\`（产物）。复制一份即可编译，不依赖外部路径。构建脚本不写死"向上几层"。

### D7 不修改官方 exe（不采用 IL 重写路线）

`[已确认]` 下载恢复靠改源码常量后重编译。IL 补丁每次官方更新即失效、无法定位问题、且属于对第三方二进制的篡改。

## 待决策（P 系列）

### P1 基座策略：继续增强 PCL 分支，还是逐步自研？`[已决策：C]`（2026-10-27）

**决定：C —— 渐进式**。新能力写在新层，旧链路仍走 PCL。详见 `decisions/0001-base-strategy.md`（Accepted）。

四条实施约束：新能力不塞进 PCL 页面；只读消费 PCL 状态；接口先行；新层功能必须可单独关闭。

| 选项 | 优点 | 代价 |
|---|---|---|
| A 继续 PCL 分支 + `custom\` 覆盖层 | 零迁移成本；下载/安装/启动/整合包全部现成；与上游可对照 | 架构受 PCL 全局配置模型限制（非实例中心）；上游同步后 23 个文件要人工比对；VB.NET + net48 生态偏旧 |
| B 以 PCL 代码为参考，重写核心、界面自建 | 架构自由（可照 Prism 的 BaseInstance）；可用 .NET 8 + C# | 工作量以月计；四大链路（下载/安装/启动/整合包）都要重做；个人自用场景收益存疑 |
| ~~C 渐进：新功能写在新层~~ **← 采用** | 风险可控；逐步替换；R1/R8 已可用不必重做 | 双栈并存期长；进程间/程序集间接口要先设计 |

理由：R1、R8 已经可用，重写这部分的收益最低；而 R2、R3、R4 都是"增量能力"，天然适合写在新层。前提是先把接口边界定下来，否则会退化成 A。

### P2 是否从 net48 迁移到 .NET 8？`[待决策]`

- 留下的理由：与 PCL 源码同构，`custom\` 覆盖层可直接生效；net48 在 Win10 上零依赖。
- 迁走的理由：.NET 8 有更好的分析器、`dotnet` CLI 生态、异步与性能；net48 的 WPF 已停止演进。
- **关键约束**：迁 .NET 8 意味着 `custom\` 那 23 个覆盖文件与上游彻底脱钩（上游是 net48 + VB），同步链路作废。所以 P2 实际依赖 P1：只有选 B/C 且新层独立成工程时才值得做。

### P3 实例模型：沿用 PCL 还是引入 Prism 式抽象？`[已决策：C 渐进新层，只读视图已接导出；第二步暂缓]`

- PCL 模型：版本目录即游戏目录，配置分散在 `Setup.ini` / 注册表 / 版本 json。
- Prism 模型：`BaseInstance` 统一接口，实例自带配置。
- **影响面**：R1（已基本满足）、R2/R4（导出需要读取实例全貌，统一接口大幅简化）、R6（联机按实例隔离也需要）。
- **建议**：若选 P1=C，在新层里定义 `IInstanceView`（只读视图）先跑通导出，不动 PCL 的存储。这是低风险起点。

**2026-10-29 第一步已落地（`custom.20`）**：新增 `Modules\Base\InstanceView.vb`——`IInstanceView` 接口（Name / PathVersion / PathIndie / DisplayName / VanillaName / Logo / Modable）+ `McInstanceView` 适配器（纯转发，不缓存、不写状态）；导出页三处版本号改经视图读取 （`modrinth.index.json` 的 `minecraft`、MCBBS `addons` 的 `game`、PCL 自有清单的 `version`）。**未做**：导入与批量操作仍直连 `McInstance`；接口只覆盖导出真正用到的字段，要加字段先问需求。

**2026-10-30 第二步暂缓（无消费者）**：全树 grep「批量」只命中 `InstanceView.vb` 自己的注释——PCL 没有批量操作功能；导入走 `ModModpack.InstallPackMCBBS`，读的是包内 manifest，不读 `McInstance`。所以视图没有第二个消费者，扩过去属空转。**触发条件**（出现即扩）：① 实现批量操作（多选启动/删除/导出）；② 实现 R2/R4 导入且导入后要读实例字段；③ 接入第二种实例格式。届时要加的字段先问需求。

### P4 导出格式先做哪个？`[已确认：导出先行]`（2026-10-28 按实际落地回填）

实际走的是**先导出**：MCBBS v2 双清单（`mcbbs.packmeta` + `manifest.json`）已实现，导出物经 **PCL 侧安装通过**；
`.mrpack` 沿用上游自带能力。导入方向（R2 读别人的包、R4 `.mrpack` 导入）**仍未做**。

- 与当初建议（先导入）相反。当时的真实需求是"把自己的实例发给别人"，所以先做导出。
- **代价**：字段理解来自读 HMCL 源码而非解包对照，所以"别人能不能读"这一环只能靠实机验——即 T-07（HMCL）/ T-08（Prism）/ T-09（Forge 分支）仍未通过。
- 若继续做导入，仍建议按 `05-formats.md` 文末的核实方法走。

### P5 安全扫描是否阻断构建？`[已确认：不自动阻断]`（2026-10-28 按实际落地回填）

- 现状：`tools\scan.ps1` 单独跑，退出码 `1` = 有高危，但**没有接入 `build.cmd`**，构建不会因漏洞失败。
- 分析器侧已放弃（`07` 第四节：老式工程 + net48，`AnalysisLevel` 不生效）。
- `[待决策]` 是否把 `scan.ps1 -Only deps` 挂到 `build.cmd` 末尾做门禁——挂上会让"有高危就没法出包"，需先修掉 Newtonsoft 13.0.0。
